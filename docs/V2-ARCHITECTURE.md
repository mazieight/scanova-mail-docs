# V1 audit and V2 migration

V1 has six ordered SQL migrations. Users and hashed sessions are global; all other mail data is currently shared. Contacts/email, identities/email, suppression/email and preferences/id are globally unique. Campaigns and drafts additionally belong to their creator. The durable recipient queue uses provider idempotency keys, stored snapshots, advisory locks, retry timestamps and recovery after uncertain sends. Webhooks verify Svix signatures before transactional/idempotent processing. Unsubscribe tokens are opaque; GET does not unsubscribe. Attachments are stored in PostgreSQL and downloaded as attachments. Provider credentials and quota configuration are global environment variables. Email branding is Scanova-only. There is no existing persisted template entity.

V2 adds an explicit Scanova tenant, memberships and session-selected tenant context. Existing IDs, messages, tokens, attachments, signatures and provider configuration remain intact. Every owned table gets tenant_id and forced PostgreSQL row-level security. Composite foreign keys prevent cross-tenant parent references, including jobs, attachments and events. Tenant context is resolved from an authenticated session and authorized membership; browser tenant identifiers alone never authorize data access. Pool connections install and clear context on checkout/release; missing context fails closed. Agency-only operations require master-admin authentication.

The migration runs transactionally, backfills Scanova before enforcing constraints, changes only uniqueness that was previously global, and adds provider/domain/template/list/audit entities. Production backup and verified restore precede migration. Rollback uses the prior application image and pre-migration database backup; no destructive reverse migration is attempted after V2 writes.

Provider connections use AES-256-GCM with a server-only master key, random nonce and connection/tenant bound associated data. Scanova's existing environment credentials remain a server-only legacy reference until securely imported; new clients never inherit them. Each connection has its own signed webhook endpoint. Delivery events must match a stored message in the resolved tenant; receiving is explicitly optional and additionally validates configured inbound domains. Client root MX records are never configured automatically.
